# /service-integration

> The Integration step of a service activity: wire this component into the call chains its neighbors already implement, so its black-box scenario tests, generated by the job from the reviewed test plan, pass against the integrated component — without touching any frozen contract.

**Arguments** — `$ARGUMENTS` is `<component_id> <activity_id>` (two space-separated tokens; `component_id` may be empty for non-component activities). Parse once; do not swap them. Work lands on the shared activity branch `activity/<activity_id>` and its single PR — you are contributing commits to a PR that already exists (or open it if this is the first phase). Do NOT open a second PR.

**Agent + skills.** Work to the standard of the **`system-architect`** agent (`.claude/agents/system-architect.md`). Follow **[[the-method-layers]]**, **[[the-method-testing]]** (§ Deterministic component scenarios) and **[[the-method-project-state]]** for all reading/updating of `.aiarch/state/project.json`.

**Goal / intention.** Per ch. 12: "features are always and everywhere aspects of integration, not implementation" — only after the components in a use case's call chain are each independently complete can that call chain be wired into a working feature. Integration is where that composition happens: it does not add business logic, it proves that already-built, independently-verified components talk to each other exactly as the committed system design's dynamic views specify. Per ch. 11, this step deserves care because integration pressure concentrates unevenly on Manager components — a Manager can find itself expected to integrate with four or five other services at once — and concurrent integration produces a nonlinear increase in complexity as issues from each service superimpose on the others, compounded by the fact that integration typically lands late in the project when there is little runway left to fix what breaks. The safer path Löwy recommends is to integrate only one or two services at a time. This step is also where the activity's two parallel branches meet: construction built the component without tests while the test-engineer bound its derived scenarios, and here the job generates and runs the scenario tests and records the run; you wire and fill hooks, and the run is the evidence the `testing` task reviews. "Done" for this step means the call-chain edges this component participates in are wired, its generated scenario tests (run by the job) pass against the real downstream stack. This step must NOT modify a frozen contract, the test plan or a generated test file (a needed contract change is a scope-change event, not an integration fix), must NOT add components outside the committed system design, and must NOT take on more concurrent neighbor integrations than the call chain actually requires.

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a send-back, retry or re-queue note) and outrank the defaults below.

1. **Read what you need** from `.aiarch/state/project.json` per [[the-method-project-state]]: the activity, the component's frozen contract, its inbound/outbound relationships in the committed system design, the frozen contracts of the specific neighbor components its call chains cross, and the component's reviewed test plans — one per contract of the component, keyed by the contract name (`.phaseArtifacts.testPlan["<contract>"]`, e.g. `reviewEngine` for `review-engine`; a component publishing several contract facets has one plan per facet, and every `.serviceContracts` entry whose `component` is this component's contract key is one of them). The test plan is a parallel branch of this activity: if it is not committed yet, do steps 2–3, commit the wiring onto `activity/<activity_id>`, say so in the integration note, `publishDraft` and stop. The `testing` task joins this step and the reviewed plan, so it holds until a run of the plan exists.
2. **Wire** this component to its integration-scope neighbors, verified against the relevant dynamic view(s), and record an integration note into the phase-artifacts store via `recordPhaseArtifact` per [[the-method-project-state]].
3. **Verify.** Call `run_checks()`.
4. **Generated tests.** The tests are already generated: the job generated them before you started. It wrote the package's `<stereotype>_scenarios.gen_test.go` and seeded `<stereotype>_hooks_test.go` if it was missing. Never edit a generated file and never change the plan.
5. **Fill the hooks.** Replace every `FILL` in `<stereotype>_hooks_test.go`. The hooks arrange the real stack: build each collaborator through its package's public constructor (the app's own component packages, wired as production wires them). Never import a package's `internal/` sub-packages, unexported identifiers or another package's test helpers, and never stand a mock or fake in for a component.
6. **Purge.** Delete every other `_test.go` in the component's package — anything that is not `<stereotype>_scenarios.gen_test.go` or the hooks file. The arch gate rejects it. The generated-tests check in `run_checks()` must be clean.
7. **Commit** the wiring and the hooks file onto `activity/<activity_id>`. Never commit `test-results/`.
8. **Publish.** `publishDraft` carries the integration note to the activity branch.
9. **Stop.** Do not mark phase status (the Manager owns that) and do not merge. Leave the PR open for the gate.
