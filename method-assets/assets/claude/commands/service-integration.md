# /service-integration

> The Integration step of a service activity: wire this component into the call chains its neighbors already implement, so its black-box scenario tests, generated by the job from the reviewed test plan, pass against the integrated component — without touching any frozen contract.

**Arguments** — `$ARGUMENTS` is `<component_id> <activity_id>` (two space-separated tokens; `component_id` may be empty for non-component activities). Parse once; do not swap them. Work lands on the shared activity branch `activity/<activity_id>` and its single PR — you are contributing commits to a PR that already exists (or open it if this is the first phase). Do NOT open a second PR.

**Agent + skills.** Work to the standard of the **`system-architect`** agent (`.claude/agents/system-architect.md`). Follow **[[the-method-layers]]**, **[[the-method-testing]]** (§ Deterministic component scenarios) and **[[the-method-project-state]]** for all reading/updating of `.aiarch/state/project.json`.

**Goal / intention.** Per ch. 12: "features are always and everywhere aspects of integration, not implementation" — only after the components in a use case's call chain are each independently complete can that call chain be wired into a working feature. Integration is where that composition happens: it does not add business logic, it proves that already-built, independently-verified components talk to each other exactly as the committed system design's dynamic views specify. Per ch. 11, this step deserves care because integration pressure concentrates unevenly on Manager components — a Manager can find itself expected to integrate with four or five other services at once — and concurrent integration produces a nonlinear increase in complexity as issues from each service superimpose on the others, compounded by the fact that integration typically lands late in the project when there is little runway left to fix what breaks. The safer path Löwy recommends is to integrate only one or two services at a time. This step is also where the activity's two parallel branches meet: construction built the component without tests while the test-engineer bound its derived scenarios, and here the job generates and runs the scenario tests and records the run; you wire, and you write no test code `[ARCH-TEST-COMPOSE]`: every generated test builds its subject from the generated `scenariocompose` package, and the run is the evidence the `testing` task reviews. "Done" for this step means the call-chain edges this component participates in are wired, its generated scenario tests (run by the job) pass against the real downstream stack. This step must NOT modify a frozen contract, the test plan or a generated test file (a needed contract change is a scope-change event, not an integration fix), must NOT add components outside the committed system design, and must NOT take on more concurrent neighbor integrations than the call chain actually requires.

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a send-back, retry or re-queue note) and outrank the defaults below.

> **When a plan binding itself is wrong.** You may not change the plan. If, after your best integration, some scenarios have a recorded failing verdict because their *binding* contradicts the contract or use case, call `reportPlanDefect` with the contract key, the failing scenario ids and a reason citing the contract or use-case clause the binding contradicts, then `publishDraft` and finish normally. The job's gate stays red. Do not put observed values in the reason. The system re-opens the test plan: a blind test-engineer checks your claim and the review rules on fault, and if the binding stands you must fix the component. Only a run whose failures are exactly the scenarios you named, with every other check green and at least one green scenario per contract, qualifies; "no verdict recorded" and harness failures do not, nor does a binding already upheld. At most two round trips per activity. The verb refuses on an activity whose lifecycle has no test plan to send back to: there, the component is what to fix.

1. **Read what you need** from `.aiarch/state/project.json` per [[the-method-project-state]]: the activity, the component's frozen contract, its inbound/outbound relationships in the committed system design, the frozen contracts of the specific neighbor components its call chains cross, and the component's reviewed test plans — one per contract of the component, keyed by the contract name (`.phaseArtifacts.testPlan["<contract>"]`, e.g. `reviewEngine` for `review-engine`; a component publishing several contract facets has one plan per facet, and every `.serviceContracts` entry whose `component` is this component's contract key is one of them). The test plan is a parallel branch of this activity: if it is not committed yet, do steps 2–3, commit the wiring onto `activity/<activity_id>`, say so in the integration note, `publishDraft` and stop. The `testing` task joins this step and the reviewed plan, so it holds until a run of the plan exists.
2. **Wire** this component to its integration-scope neighbors, verified against the relevant dynamic view(s), and record an integration note into the phase-artifacts store via `recordPhaseArtifact` per [[the-method-project-state]].
   - **The composition root.** Integrating a Manager or a Client also builds the server. The job has already run `go tool appgen`, so `cmd/server/main.gen.go`, `config.gen.go`, the Manager's Temporal layer, `internal/client/**` and `api/openapi.yaml` exist; never edit a generated file. Commit them with your wiring. The job seeds `cmd/server/hooks.go` once, and that file is yours: replace every `FILL` panic in it with the app's own answer (the authorization policy, an external service's URL). The policy decides verbs for the authenticated principal's own scope (every row of the generated `cmd/server/authz.gen.go`, which `TestPolicyAdmitsEveryGeneratedRequest` checks); ownership of data-held resources is the Manager's, keyed on `rc.Principal.Subject`. The platform owns who is acting: the edge authenticates and every Manager op already receives the caller as `rc.Principal`, so wire no sign-in, token check or identity service, and do not copy the principal into a workflow input or a request: it already travels with the workflow. A machine client's code is all generated, and its contract is derived from the Manager behind it, so its task is to commit that code and fill the composition hooks. Its scenario tests build the generated handler bound to the real Manager from `scenariocompose`; there is no test wiring of yours.
3. **Verify.** Call `run_checks()`.
4. **Generated tests.** The tests are already generated: the job generated them before you started. It wrote the package's `<stereotype>_scenarios.gen_test.go` and `null.gen_test.go` (the switch the null-subject run uses). Each builds its subject, the principals and the arranged world from the plan and the generated `scenariocompose` package, so you write no test code and fill nothing in `[ARCH-TEST-COMPOSE]`. Never edit a generated file and never change the plan. The platform's gates over the tests are the drift check (`gen-tests-check`, which also reports a hooks file left from an earlier run: delete it), the scenarios (`test-scenarios`) and the null-subject run (`test-discriminate`): it re-runs every scenario once per stimulus operation with that operation doing nothing, and a scenario that still passes is reported as `TP-DISCRIMINATE <component> <scenario> <operation>` because it would pass without the behavior it claims to test. A survivor is a defect of the binding, not of the component: you cannot fix it by editing the component or the plan, so name the scenario and what its stimulus should have changed in the integration note.
5. **Purge.** Delete every other `_test.go` in the component's package: anything that is not `<stereotype>_scenarios.gen_test.go` or `null.gen_test.go`, a leftover `<stereotype>`-named hooks file above all. The arch gate rejects it `[ARCH-TEST-COMPOSE]`. The generated-tests check in `run_checks()` must be clean.
6. **Commit** the wiring and the generated tests onto `activity/<activity_id>`. Never commit `test-results/`.
7. **Publish.** `publishDraft` carries the integration note to the activity branch.
8. **Stop.** Do not mark phase status (the Manager owns that) and do not merge. Leave the PR open for the gate.
