# /system-draft

> Draft (or amend) the **System (layered decomposition + use-case realizations)** artifact as one design-rail CI job. The job's ambient env fixes the artifact kind and target slot.

**Arguments** — none. Kind, job mode, branch, and project come from the ambient `AIARCH_*` env baked into this CI run.

**Agent + skills.** **Adopt the `system-architect` role**: read `.claude/agents/system-architect.md` and act per that charter yourself, in this session. Do NOT dispatch a subagent or use an Agent/Task tool — the CI job runs single-session; you ARE the system-architect. Follow **[[the-method-architecture]]** (including its "Draft-job doctrine" section — that is your task statement) and **[[the-method-project-state]]** for the tool flow.

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a dispatch note or a send-back) and outrank the defaults below. The note also outranks any critic verdict item that contradicts it or that it puts out of scope: make the amendment it asks for even with no open comment or verdict, and do not re-affirm a draft unchanged while a note asks for a change.

> **State changes go through the `aiarch-state` MCP tools, not hand-edits.** Never hand-edit `.aiarch/state/project.json`; never run `git` for state.

1. **Read your inputs.** `getCommittedSlot` for every committed predecessor slot this artifact builds on; on an amendment, `getDraftSlot` for the current draft (basis: all Phase-1 predecessors).
2. **Read the review ledger** with `getReviewThread`. If open comments exist, this is a redraft: your draft MUST address every open comment. Also read `getCritique` — if it carries a `revise` verdict, its notes are the PM's revision guidance and your draft MUST address them. Also read the current draft slot's `notes` field (`getDraftSlot`) — founder rejection/send-back feedback lands THERE, not in the review thread; every point in it MUST be addressed (answer each via `respondToReviewComment` where a matching comment exists, otherwise in your `publishDraft` message).
3. **Draft** the typed model per [[the-method-architecture]] — the static decomposition AND the realizations, which are part of THIS artifact, not a follow-up. Every use case in the committed `.coreUseCases` (core and every nonCore variation) carries a dynamic view whose `steps` realize its activity diagram node by node: one ordered, non-empty call fragment per `action`/`timeEvent`/`acceptEvent` node, rooted per that path's entry kind (`actor → Client` from a `start`, the scheduling `Client → Manager` call from a `timeEvent`, the queued `Manager → Manager` call from an `acceptEvent`), with both Client surfaces drawn as step-local `alt` groups wherever the Manager operation rides both. A view left with no steps is an unrealized use case, not a draft in progress. Submit with `putDraftModel` — it validates the whole `CC-*` correspondence family at **Error** severity and returns actionable errors; fix and resubmit until accepted.
   - **Every built Client states its `surface`** — `web` (a page people use in a browser), `mcpApp` (a UI people use inside an MCP host; hand-built like `web`), `rest` (the shared generated HTTP API, at most one) or `mcpTools` (generated MCP tool tables). `putDraftModel` refuses a built Client without one (`SYS-CLIENT-SURFACE`).
   - **The mission's `deliverySurfaces` decide which Clients the System must have**: each listed kind needs a Client with that `surface` `[SYS-SURFACE-REQUIRED]`; an MCP tool server is not an MCP Apps UI, so the kinds must match exactly. In every use case an actor enters through a call into each required surface they use, drawn as one `alt` group at their first step `[SYS-SURFACE-ENTRY]` (a per-use-case waiver on the System is the only exception). A surface the platform cannot generate yet is refused (`GEN-SURFACE-SUPPORTED`).
   - **A `rest` or `mcpTools` Client is machine-facing.** Leave its `constructionProfile` unset: `generated` would drop the activity that tests it through its own transport. In each step where an actor calls a machine client, draw that client's call into the Manager in the same step, naming the operation: the client's contract and scenarios are derived from exactly that, so a request with no such call beside it is refused (`SYS-CLIENT-MACHINE-CALL`).
   - **A call from an actor into a browser surface leads with the operations it performs.** Write `AddTodo | RewordTodo — performs one list action`: exported names, `|` between alternatives, prose after the `—`. The surface's contract is derived from exactly these names, so `requests one list action` is refused (`SYS-CLIENT-OP-LABEL`). `|` separates only before the first `—` or `→`; after them, as in `ListTodos(filter) → items | empty`, it is prose. In a call to a component that has a contract, every `|` alternative must name one of its operations (`TP-LABEL-OP`).
   - **The platform owns who is acting; never design it.** The framework edge authenticates every caller (and under the `local` profile injects the dev principal, so opening the app needs no sign-in step), and every Manager operation already receives the caller as `rc.Principal`. Never draw an identity provider as a Resource, never add a ResourceAccess that verifies who the caller is, never give an operation a field that authenticates or identifies the caller (a token, proof, session or "actor" argument), and never draw a sign-in step, redirect or cookie in a Client. Whose data a request touches is the Manager's call, keyed on `rc.Principal.Subject`. See [[platform-runtime-doctrine]] entry 10.
   - **The outcome returns to the Client that asked** (`UC-OUTCOME-AT-ASKING-SURFACE`, Error). For every derived scenario, after the node where the actor first acts on a Client, the path must carry [UC-OUTCOME-AT-ASKING-SURFACE] EITHER (1) a step on a later node with a call INTO that same asking Client (the system returning the state to the surface that asked), followed on the path by an `objectNode`, or an `objectNode` drawn in that Client's or the actor's own lane; OR (2) a `sendSignal` to that actor (`linkedActorId`) that is unlaned or drawn in the asking Client's or the actor's lane. The asking `actor → Client` step itself never counts [UC-OUTCOME-AT-ASKING-SURFACE]. A `sendSignal` in another component's lane, an outcome shown only on another surface, and a `subscribe` drawn `Client → MessageBus` (a call OUT of the Client, not into it) do not count.
   - **A Resource someone writes is read by someone** (`SYS-RESOURCE-UNREAD`, Error). A Resource with an inbound relationship must be read: a relationship leaves it, or a non-ResourceAccess has a relationship into it (a Client subscription), or some dynamic-view call into a ResourceAccess over it is drawn "op(args) → what it returns" [SYS-RESOURCE-UNREAD]. An `encapsulates` note that defers the read to operational concepts does not discharge it: draw the reader in the use case that needs it [SYS-RESOURCE-UNREAD]. A notice channel written by `announceListChanged(owner)` and read by nothing leaves a ResourceAccess contract of one void op no test plan can observe.
   - **Every relationship is called by some view.** Draw the call in the use case that makes it, or remove the relationship (`CC-EDGE-REALIZED`). The one exception is an ambient dependency on a Utility no use case can narrate: logging, diagnostics, authentication. Mark that relationship `ambient: true`; it is illegal on anything but a Utility, and it exempts no operation from being reached. Pub/sub is never ambient: it is business work, so draw it.
   - **If a chain will not draw, STOP.** Do not add, split, or reshape a component to make it draw; do not demote a node to a `note` to clear a coverage finding; do not invent a call with nothing behind it. Each of those makes the gate the reason the model changed, which is the one thing the gate must never be. When the cause is the core use case itself — an `action`/`timeEvent`/`acceptEvent` node at which no component makes a NEW call, because it only returns or renders a result an earlier node produced, or refuses on a verdict an earlier check already returned — call **`reportUpstreamDefect`** with `gate: "coreUseCasesReview"`, the `nodeRefs` (`{useCase, node}`: the use case's name or id and the node's id in the committed core use cases) and a `rationale` that says, per node, which earlier node already produced what it shows and why no honest call realizes it. Then call `publishDraft` and finish without a System draft: the system sends the core use cases back through their own review with your rationale, and re-dispatches this draft once the amendment is committed. The same holds when `putDraftModel` is refused by a core-use-case rule (`UC-*`, e.g. `UC-OUTCOME-AT-ASKING-SURFACE`, `UC-LANE-RESOLVES`) caused by the committed use case's own shape (different actors' entries merged then re-split by who asked; one actor acting on two Clients at one node): no System fixes it, so call **`reportUpstreamDefect`** with `ruleFindings` `[{ruleId, useCase, scenario?}]` exactly as the refusal named them, and a `rationale`. The server admits one only when that rule is a core-use-case rule reporting an Error at that use case (and scenario) against the committed core use cases and the System this session last gave `putDraftModel`. `nodeRefs` stay `action`/`timeEvent`/`acceptEvent` nodes only, not a decision or a sendSignal; give at least one nodeRef or ruleFinding. Never edit the core use cases yourself. A missing component or edge is not an upstream defect: the decomposition is this draft's own to get right on its merits.
4. **Respond to every open ledger comment** with `respondToReviewComment` — accept (say what you changed) or rebut (say why not, grounded in the Method). Silent non-response is a defect.
5. **Finish** with `publishDraft` (exactly once). Do not open PRs, do not merge, do not touch phase status — the server owns the loop. If dispatched as a redraft and you find no open review comments, no revise verdict, AND no unaddressed rejection notes on the draft slot, do not exit without publishing: re-validate the existing draft and call `publishDraft` anyway to re-affirm it. A draft job must NEVER end without calling `publishDraft` — an empty exit fails the run's silent-failure guard.
