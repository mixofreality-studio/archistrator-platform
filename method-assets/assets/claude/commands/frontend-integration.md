# /frontend-integration

> The Integration step of a frontend activity: wire this UI surface into the real call chains its neighboring Managers/Engines already implement, so its black-box flow tests, generated by the job from the reviewed flows, pass against the integrated surface — without touching any frozen contract or approved design.

**Arguments** — `$ARGUMENTS` is `<component_id> <activity_id>` (two space-separated tokens; `component_id` may be empty for non-component activities). Parse once; do not swap them. Work lands on the shared activity branch `activity/<activity_id>` and its single PR — you are contributing commits to a PR that already exists (or open it if this is the first phase). Do NOT open a second PR.

**Agent + skills.** Work to the standard of the **`system-architect`** agent (`.claude/agents/system-architect.md`). Follow **[[the-method-layers]]**, **[[the-method-testing]]** (§ Deterministic component scenarios) and **[[the-method-project-state]]** for all reading/updating of `.aiarch/state/project.json`.

**Goal / intention.** Per ch. 12: "features are always and everywhere aspects of integration, not implementation" — only once the pieces of a use case's call chain are each independently complete can that call chain be wired into a working feature. A frontend surface is no exception: it becomes a feature only once it is wired against the real Managers/Engines it calls, not while it is still standing alone against a mock. Per ch. 11's own worked project-design example, this is exactly how Löwy schedules Client work: Client construction happens first against simulators of the Managers it depends on, with an explicit, separate integration activity added once the real Managers are complete — because integration pressure concentrates unevenly on Manager-facing components (the same chapter shows Managers integrating with four or five other services at once) and because concurrent integration produces a nonlinear increase in complexity that lands late in the project, when there is little runway left to fix what breaks. Löwy's recommendation is to integrate only one or two services at a time. This step is also where the activity's two parallel branches meet: construction built the surface without tests while the test-engineer bound its derived flows, and here the job generates and runs the flow tests and records the run; you wire, and you write no test code `[ARCH-TEST-COMPOSE]`: a web flow is a generated Playwright spec that locates every element by the role and name of the approved design, an MCP client's scenario builds its subject from the generated `scenariocompose` package, and the run is the evidence the `testing` task reviews. "Done" for this step means the call-chain edges this surface participates in are wired against the real, frozen contracts of its neighbors, replacing whatever simulator or mock it was constructed against, its generated flow tests (run by the job) pass. This step must NOT modify a frozen contract, the approved UI design concept, the flows (test plan) or a generated test file (a needed change to either is a scope-change or amend event, not an integration fix), must NOT add components outside the committed system design, and must NOT take on more concurrent neighbor integrations than this surface's flows actually require.

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a send-back, retry or re-queue note) and outrank the defaults below.

> **When a plan binding itself is wrong.** You may not change the plan. If, after your best integration, some scenarios have a recorded failing verdict because their *binding* contradicts the contract or use case, call `reportPlanDefect` with the contract key, the failing scenario ids and a reason citing the contract or use-case clause the binding contradicts, then `publishDraft` and finish normally. The job's gate stays red. Do not put observed values in the reason. The system re-opens the test plan: a blind test-engineer checks your claim and the review rules on fault, and if the binding stands you must fix the component. Only a run whose failures are exactly the scenarios you named, with every other check green and at least one green scenario per contract, qualifies; "no verdict recorded" and harness failures do not, nor does a binding already upheld. At most two round trips per activity. The verb refuses on an activity whose lifecycle has no test plan to send back to: there, the component is what to fix.

1. **Read what you need** from `.aiarch/state/project.json` per [[the-method-project-state]]: the activity, this surface's approved UI design concept, its Client/SPA entry (relationships in/out) in the committed system design, the frozen contracts of the specific Manager/Engine neighbors its flows cross, and the surface's reviewed flows — one test plan per contract of the surface, keyed by the contract name (`.phaseArtifacts.testPlan["<contract>"]`: the surface's own contract, e.g. `webClient` for `web-client`, and every facet whose `.serviceContracts` entry names it as `component`, e.g. `webClientBilling`). The flows are a parallel branch of this activity: if they are not committed yet, do steps 2–3, commit the wiring onto `activity/<activity_id>`, say so in the integration note, `publishDraft` and stop. The `testing` task joins this step and the reviewed flows, so it holds until a run of the flows exists.
2. **Wire** this surface to its integration-scope neighbors, verified against the relevant flows/dynamic view(s), and record an integration note into `.phaseArtifacts.integrationNote` via `recordPhaseArtifact` per [[the-method-project-state]].
   - **The UI tests are a project of their own.** `uitests/package.json` is already seated; `run_checks()` installs it and the job's check installs its browser. Commit `uitests/package-lock.json` with the generated tests.
   - **The local stack authenticates through the framework, not through your edit.** The composition root (`cmd/server/hooks.go` and the generated `cmd/server/*.gen.go`) is outside a surface's scope: never edit it, and never add a dev principal, a mount or a route there. Under the `local` profile the generated auth edge injects the one principal named by the app's `<ENV_PREFIX>_DEV_PRINCIPAL` setting (the prefix of every variable in `cmd/server/config.gen.go`; its `devPrincipalEnv` constant names it); unset, the edge denies with 401, and set under any other profile the app refuses to boot. So when the harness boots the app, set that variable to the subject the flow acts as. A 401 from the local stack means it is unset, not that the composition root needs a change.
3. **Verify.** Call `run_checks()`. The integration gate boots the composed app through its run contract (`smoke:composition`: `/readyz`, the SPA page and every MCP tool the model generates, then a teardown that leaves nothing behind), and the web scenarios run through the scenario host (`go tool webscenarios`), which boots the app and serves the arrange endpoint the browser calls; machine-client scenarios run over the wire as the plan's principals `[TP-PRINCIPAL]`.
4. **Generated tests.** The tests are already generated: the job generated them before you started. A web surface has, per contract, Playwright specs, config, reporter, an element inventory and a surface check under `uitests/generated/<contract>/`; an MCP client has `<stereotype>_scenarios.gen_test.go` and `null.gen_test.go` in its Go package. You write no test code and fill nothing in `[ARCH-TEST-COMPOSE]`. Never edit a generated file and never change the flows. Two gates are specific to a web surface. The surface check (`surface-check`, the generated `surface.spec.gen.ts`) opens every screen of the approved design and asserts each non-repeating element is on it by its role and accessible name, and it runs before any flow; when it fails, the built surface does not match its design, so fix the surface's markup (a native element of the design's role, named as the design names it), never the design or the flow `[UID-NAME]`. The flows then assert what the user sees the instant an action lands, with every call to the server delayed; a surface that waits for the server to show the user's own gesture fails there, so fix the surface. The drift check (`gen-tests-check`) also reports a hooks file left from an earlier run: delete it. The null-subject run (`test-discriminate`, `TP-DISCRIMINATE`) re-runs Go scenarios with their stimulus operation doing nothing; it also runs each web scenario through the scenario host (`go tool webscenarios`) with the Manager operation its step drives nulled in the server the host launches, so a flow that still passes without the server doing the work is a survivor of the binding, not of the surface: name it in the integration note.
5. **Purge.** Delete every test of this surface that the generator did not write: any `*.test.ts`/`*.test.tsx` in the surface's code under `webApp/src/`, any hand-written spec for it under `uitests/` outside `uitests/generated/`, and, for an MCP client, any `_test.go` in its package other than the generated scenarios file and `null.gen_test.go`. The arch gate rejects them `[ARCH-TEST-COMPOSE]`. The generated-tests check in `run_checks()` must be clean.
6. **Commit** the wiring and the generated tests onto `activity/<activity_id>`. Never commit `test-results/` or `uitests/test-results/`.
7. **Publish.** `publishDraft` carries the integration note to the activity branch.
8. **Stop.** Do not mark phase status (the Manager owns that) and do not merge. Leave the PR open for the gate.
