# /service-test-plan <componentId> <activityId>

> The Test Plan step of a service activity: bind this component's deterministic scenarios to concrete values, in parallel with construction, so the integration task can generate the black-box tests from them and run them against the integrated component.

**Arguments** — `$ARGUMENTS` is `<component_id> <activity_id>` (two space-separated tokens). Parse once; do not swap them. Work lands on the shared activity branch `activity/<activity_id>` and its single PR — you are contributing commits to a PR that already exists. Do NOT open a second PR.

**Agent + skills.** Work to the standard of the **`test-engineer`** agent (`.claude/agents/test-engineer.md`). Follow **[[the-method-testing]]** (§ Deterministic component scenarios) and **[[the-method-project-state]]** for all reading/updating of `.aiarch/state/project.json`.

**Goal / intention.** Per ch. 9, a test engineer is "not a tester, but a full-fledged software engineer" whose code exists to break the system; per App A the Service Test Plan is its own branch of the activity, written beside construction and joined with it at testing. On this platform the plan's *scenarios* are not yours to invent: they are derived deterministically from the committed use-case activity diagrams (the I/O-explicit activity-diagram technique — one stimulus per path, every elementary path, each loop unrolled once), and this component's plan is every scenario in which some stimulus is an input to it. Your job is the *binding*: the concrete values, expected results and probes that turn each derived scenario into a black-box integration test the integration task runs against the real downstream stack. "Done" means every projected scenario is bound and the TP-* rules pass. This step must NOT write test code, must NOT add or drop scenarios, and must NOT bind against the implementation (you see the contract and the use cases, never the component source).

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

**Sent back from integration.** If your operator notes report plan defects, integration has alleged that named scenarios' bindings contradict the contract or use case. The note is a claim to check, not evidence. Re-derive only the named bindings from the contract and the use case, and change them only where the claim holds; if a binding follows from the contract and use case, leave it exactly as it is, because integration must then fix the component. Do not add or drop scenarios, and do not change a binding the note does not name. Never copy a value from the implementation or from an observed result into a binding. To let a binding stand, still re-record the plan unchanged with `recordPhaseArtifact`, then `publishDraft`: the job fails a run that does not advance the branch, and an unchanged plan publishes a re-affirm commit.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a send-back, retry or re-queue note) and outrank the defaults below.

1. Call `listComponentScenarios` with the contract key (once per contract facet, when the component has several). Each scenario has stimuli (inputs into this component), expected outputs, expected states and hints. Do NOT invent scenarios; the set is derived from the use cases.
2. **The binding is a record, not code.** The plan is a typed record the platform turns into the test; there are no hooks and no escape hatches `[TP-HOOK]`: a plan carrying a field the model does not have (a per-step hook flag or an output waiver, both retired, among them) is refused when it is recorded, and so is an arrange call that performs the scenario's own stimulus. For every scenario `listComponentScenarios` returned, write one binding `{scenario, arrange, steps, skip}`, and for every stimulus one step `{seq, operation, inputs, expect, probes}`:
   - **`inputs`** are the operation's params, each `{name, value}` where `value` is `{"kind":"literal","model":{"json":<the value>}}` or `{"kind":"ref","model":{"step":<n>,"path":"<field path>"}}` (add `"probe":<i>` to read probe i of that step). A literal must satisfy the param's schema. A value the component mints at run time, such as an id an earlier step returned, is a `ref` to that step's result and never a literal or prose such as `id from step 2` `[TP-ARG-REF]`: the step must be earlier (or, for a probe, the same step) and the path must exist in the result schema.
   - **`expect`** is what the step returns: `result` (a JSON subset of the result) or `errorExpected` with the contract's `errorCode`. Every step asserts something, itself or through its probes `[TP-EXPECT-REQUIRED]`; an empty string, `{}`, `[]` or a missing `expect` where the contract promises something is refused. A value the contract's error model refuses is bound as `errorExpected` with its code; an empty credential the contract refuses cannot expect success.
   - **`probes`** prove each expected state and observable output of the stimulus, each `{for: <node id>, component, operation, inputs, expect}`. A probe calls a read-only operation of a designed contract and is for a node on this scenario's path `[TP-PROBE]`; every expected state and every expected output has a probe for its node `[TP-STATE]`. There is no escape for an output nobody can observe: an output no contract can show is a design defect to flag, not a binding to write. The generated test reads each probe before and after the step, and a step whose every probe already held before it ran fails as `vacuous`, so choose the observation the stimulus changes. Add `before` (an `expect` for the first probe, read before the step runs) to state the world the stimulus starts from.
   - **`arrange`** is the scenario's setup, run before the first step, from exactly four kinds, each `{"kind":..., "model":{...}}` `[TP-ARRANGE]`: `contractCall` (a designed operation, with typed inputs, that builds state), `advanceClock` (a Go duration), `failNext` (the next call of a designed operation fails with an `errorCode`), `seedResource` (a fixture loaded into a Resource component). Setup that none of the four can express is not yours to improvise: there is no fifth kind, so flag the gap back to the contract's owner (the `senior-developer`).
   - **`principals`**, on the plan, name every actor that originates a stimulus of a scenario you bind: `{"<actor id>": {"subject": "...", "roles": ["..."]}}` `[TP-PRINCIPAL]`. The test runs each stimulus as that actor; you never write who is acting into an input.
   - **A Client's stimulus has the actor's outcome to observe.** When the use case shows the actor something after the stimulus, the step observes it `[TP-ACTOR-OBSERVED]`: a machine client through a probe for the node.
   - **Bind what the contract and use case say, never a blank.** Never leave a blank placeholder: an empty value, an empty object or a missing `expect` where the contract promises something is a defect, not a default.
   - **A machine client's scenarios run through that client.** Its contract is derived: one operation per route or tool, spelled as the Manager's name without its stereotype and then the operation (`ListAddTodo`). An input is named as the Manager's param. A scenario's expectations are what the actor sees over this transport: an MCP tool's result sits under `result` as `{"result": ...}`, a REST route answers with the bare value, and a refusal is bound by the Manager's error kind on both, such as `errorCode: NotFound`. Show that the request reaches the right operation and that the actor sees the result or the refusal; the Manager's scenarios own its business rules, so do not re-prove them here.
3. A scenario may be skipped only with `skip: {reason, until: <activityId>}` naming an upstream activity not yet integrated.
4. `recordPhaseArtifact` with mapKey = the contract key (the `.serviceContracts` key, e.g. `billingEngine` for `billing-engine`) and payload `{"testPlan": {...}}` whose `component` is that same key. A plan is filed under its contract key and nothing else: the generated test, its results and the checks that read them are all named by it. A component publishing several contract facets has one plan per facet, each under its facet's key. The verb fails on any TP-* finding, and each finding names the rule; fix and retry.
5. `publishDraft`.
6. **Stop.** Do not mark phase status (the Manager owns that) and do not merge. Leave the PR open for the gate.
