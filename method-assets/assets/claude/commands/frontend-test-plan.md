# /frontend-test-plan <componentId> <activityId>

> The Flows step of a frontend activity: bind this UI surface's deterministic scenarios to concrete user actions and observables, in parallel with construction, so the integration task can generate the black-box flow tests from them and run them against the integrated surface.

**Arguments** — `$ARGUMENTS` is `<component_id> <activity_id>` (two space-separated tokens). Parse once; do not swap them. Work lands on the shared activity branch `activity/<activity_id>` and its single PR — you are contributing commits to a PR that already exists. Do NOT open a second PR.

**Agent + skills.** Work to the standard of the **`test-engineer`** agent (`.claude/agents/test-engineer.md`). Follow **[[the-method-testing]]** (§ Deterministic component scenarios) and **[[the-method-project-state]]** for all reading/updating of `.aiarch/state/project.json`.

**Goal / intention.** Per ch. 9, a test engineer is "not a tester, but a full-fledged software engineer" whose code exists to break the system; per ch. 11 a Client's test plan is scheduled early, exactly like a service's. On this platform the *scenarios* are not yours to invent: they are derived deterministically from the committed use-case activity diagrams, and this surface's plan is every scenario in which some stimulus is a user action on it. Your job is the *binding*: for each stimulus the concrete user actions on the approved design's screens (`{"kind":"click|fill|navigate|check|uncheck|dblclick|hover|press|select","model":{"target":{"element":"<ui-design element id>"},...}}`) and the observable that proves the expected outcome (`{"kind":"visible|hidden|absent|text|value|checked|unchecked|enabled|disabled|focused|count|url","model":{...}}`), turned into a Playwright flow the integration task runs against the integrated system. "Done" means every projected scenario is bound and the TP-* rules pass. This step must NOT write test code, must NOT add or drop scenarios, and must NOT judge the design concept's aesthetics (you see the approved design and the use cases, never the surface's source).

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

**Sent back from integration.** If your operator notes report plan defects, integration has alleged that named scenarios' bindings contradict the contract or use case. The note is a claim to check, not evidence. Re-derive only the named bindings from the contract and the use case, and change them only where the claim holds; if a binding follows from the contract and use case, leave it exactly as it is, because integration must then fix the component. Do not add or drop scenarios, and do not change a binding the note does not name. Never copy a value from the implementation or from an observed result into a binding. To let a binding stand, still re-record the plan unchanged with `recordPhaseArtifact`, then `publishDraft`: the job fails a run that does not advance the branch, and an unchanged plan publishes a re-affirm commit.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a send-back, retry or re-queue note) and outrank the defaults below.

1. Call `listComponentScenarios` with the contract key (once per contract facet, when the component has several). Each scenario has stimuli (user actions on this surface), expected outputs, expected states and hints. Do NOT invent scenarios; the set is derived from the use cases.
2. **The binding is a record, not code.** The plan is a typed record the platform turns into the Playwright flow; there are no hooks and no escape hatches `[TP-HOOK]`: a plan carrying a field the model does not have (a per-step hook flag or an output waiver, both retired, among them) is refused when it is recorded. For every scenario `listComponentScenarios` returned, write one binding `{scenario, arrange, steps, skip}`, and for every stimulus one step `{seq, operation, inputs, expect, probes}`:
   - **The action** is the step's one input, named `action`, a literal `{"kind":"literal","model":{"json":<action>}}` whose JSON is `{"kind":"<kind>","model":{...}}` `[TP-UI-ACTION]`: exactly one action per step, because a step with none does nothing and asserts a state that already holds. The kinds are `navigate` (`route`, a screen route of the design `[UID-ROUTE]`), `click`, `dblclick`, `hover`, `check`, `uncheck` (each `target`), `fill` (`target`, `value`), `press` (`target`, `key`, e.g. `Enter` or `Escape`) and `select` (`target`, `option`).
   - **Targets are design element ids.** A `target` is `{"element":"<id>"}` (add `"nth"` for the nth instance of a repeating element) naming an element of the approved design in `.phaseArtifacts.uiDesign[<component_id>]`; the platform finds it by the role and accessible name the design gives it, so you never name the DOM `[TP-UI-TARGET]`. The target must exist in the design and its role must be one the action can act on; a `count` is of an element the design marks `repeats`. A route you navigate to or observe must be a screen route of the design `[UID-ROUTE]`.
   - **`expect.result`** is what the user sees afterwards: a string holding a JSON array of one or more observables, each `{"kind":"<kind>","model":{...}}`, each stating exactly one thing. The kinds are `visible`, `hidden`, `absent`, `checked`, `unchecked`, `enabled`, `disabled`, `focused` (each `target`), `text` (`target`, `text`), `value` (`target`, `value`), `count` (`target`, `n`) and `url` (`route`). An empty array or no observable at all is refused `[TP-EXPECT-REQUIRED]`; `text` or `value` with `""` states that the element is empty, so write it only when empty is the outcome. When the use case shows the actor something after the action, a step observes it `[TP-ACTOR-OBSERVED]`. Add `before` (`{"result": <the same kind of observation>}`) to state what the user sees before the action; a step whose assertions were already true before it ran proves nothing, so observe what the action changes.
   - **Values are literals or refs.** A value the system mints at run time, such as an id shown after an earlier step, is a `ref` `{"kind":"ref","model":{"step":<n>,"path":"..."}}` to an earlier step, never prose such as `id from step 2` `[TP-ARG-REF]`.
   - **`arrange`** is the scenario's setup, run before the first step, from exactly four kinds, each `{"kind":..., "model":{...}}` `[TP-ARRANGE]`: `contractCall` (a designed operation that builds state through the real stack), `advanceClock`, `failNext` (the next call of a designed operation fails with an `errorCode`) and `seedResource`. A setup none of the four can express is flagged back to the contract's owner; there is no fifth kind.
   - **`principals`**, on the plan, name every actor that originates a stimulus of a scenario you bind: `{"<actor id>": {"subject": "...", "roles": ["..."]}}` `[TP-PRINCIPAL]`. An agent actor's principal also declares `onBehalfOf`, the delegating human's subject `[TP-PRINCIPAL-DELEGATION]`.
   - **Every step carries a real value and a real expectation.** Never leave a blank placeholder: an empty target or a missing observable is a defect, not a default. An expectation equal to the operation's zero result is almost certainly vacuous `[TP-EXPECT-ZERO]`: bind the discriminating fields of what the user sees.
   - **Say what the user does, not how the control is built.** The platform checks that the design's role takes the action (a `check` needs a checkbox or switch, a `fill` a textbox) and that the built surface has every element the design names, so choose the action the user takes and let the role check hold you to the design.
3. A scenario may be skipped only with `skip: {reason, until: <activityId>}` naming an upstream activity not yet integrated.
4. `recordPhaseArtifact` with mapKey = the contract key (the `.serviceContracts` key, e.g. `billingEngine` for `billing-engine`) and payload `{"testPlan": {...}}` whose `component` is that same key. A plan is filed under its contract key and nothing else: the generated test, its results and the checks that read them are all named by it. A component publishing several contract facets has one plan per facet, each under its facet's key. The verb fails on any TP-* finding, and each finding names the rule; fix and retry.
5. `publishDraft`.
6. **Stop.** Do not mark phase status (the Manager owns that) and do not merge. Leave the PR open for the gate.
