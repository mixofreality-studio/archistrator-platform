# /frontend-detailed-design

> The Design step of a frontend activity: produce this UI surface's design concept — layouts, component choices, flows, states — and hand it to review before construction begins.

**Arguments** — `$ARGUMENTS` is `<component_id> <activity_id>` (two space-separated tokens; `component_id` may be empty for non-component activities). Parse once; do not swap them. Work lands on the shared activity branch `activity/<activity_id>` and its single PR — you are contributing commits to a PR that already exists (or open it if this is the first phase). Do NOT open a second PR.

**Agent + skills.** Work to the standard of the **`ui-designer`** agent (`.claude/agents/ui-designer.md`). There is no dedicated UI-design Method skill — this step's design work is scoped by the agent's own remit. Once produced, the design concept is reviewed via **[[the-method-review-routing]]** (founder/architect-user approval plus `ux-reviewer`, `product-manager`, and `system-architect`), not amended or frozen unilaterally. Follow **[[the-method-project-state]]** for all reading/updating of `.aiarch/state/project.json`.

**Goal / intention.** Per ch. 14's scope-versus-effort model, Löwy places "the services detailed design or Clients user interface" in the same tier of the design hierarchy: narrower in scope than architecture but far more time-consuming, running to weeks of work even for a handful of interacting parts. The book has no Appendix-B-style rulebook for UI-design method the way it does for service contracts, so the nearest real anchor is the chapter's own hand-off doctrine: a designer with authority over one piece of work produces a concrete design before anyone builds against it, and that design is never handed straight to construction — it goes to review, and only a reviewed, approved design is safe to construct against. This step is that discipline applied to one UI surface: produce the design concept — the layouts, component choices, flows, and states — that covers every core use case and persona journey captured in Requirements, and stop short of writing code. "Done" means a design concept exists that traces to Requirements and is ready for [[the-method-review-routing]] to gate; it does not mean the concept has been approved, and it certainly does not mean any surface has been built. This step must NOT write production UI code, must NOT change the committed system design, and must NOT let the concept proceed to construction unreviewed.

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a send-back, retry or re-queue note) and outrank the defaults below.

> **State changes go through the `aiarch-state` MCP tools, not hand-edits.** Where a step below says to record a service contract, phase artifact, or testing artifact and "commit onto branch", do it with the matching tool — `recordServiceContract` / `recordPhaseArtifact` / `recordTestingState` — and finish with `publishDraft`. Do **not** hand-edit `.aiarch/state/project.json` or run `git` for state; only source/doc **files** (code, docs) are git-committed by you. See [[the-method-project-state]].

1. **Read what you need** from `.aiarch/state/project.json` per [[the-method-project-state]]: the activity, this surface's UX requirements from the Requirements phase, its entry (Client/SPA container, relationships to the Managers/Engines it calls) in the committed system design, and the core use cases and personas it must support.
2. **Produce** the phase artifact: the UI design for this surface, recorded to `.aiarch/state/project.json` → `.phaseArtifacts.uiDesign[surface]` via `recordPhaseArtifact` per [[the-method-project-state]], then committed onto branch `activity/<activity_id>` and handed to review via [[the-method-review-routing]]. Recording it also writes this surface's contract, one operation per name the System's dynamic views lead with in actor calls into it. You author none of that, and each re-record rewrites it. If the operations it derives are wrong, the System's labels are what to change, which is a design amendment.
   - **The design is a typed record, not prose.** It is `{surface, screens, content}`. Each screen is `{id, route, elements}`; each element is `{id, role, name, within, repeats}`. The element id is the key every test step targets, and the role and accessible name are the only place a control's locator is written down: the platform derives the test's locator from them (`getByRole(role, {name})`), so what you write here is what the built surface must expose and what a user or assistive technology finds it by. `content` is narrative for the reviewers (layouts, states, flows) and nothing reads it.
   - **Every element is well-formed.** `role` is one of the closed role set (button, checkbox, textbox, listitem, list, link, heading, status, dialog, navigation, main, form, option, combobox, switch, tab, tabpanel, table, row, cell, img) `[UID-ROLE]`. A control is found by what it is called, so every role except the structural ones (list, main, navigation, form) has a `name` that says what the control does `[UID-NAME]`: a toggle named for its action or its item, never "checkbox". Ids are unique across the design `[UID-ID-UNIQUE]`. `within` names another element of the same screen (the list that holds the row, the form that holds the field) `[UID-WITHIN]`. `repeats` is true on an element that appears once per item, so a test may count or index it. Every screen has a `route`, and the routes are what a test navigates to and observes `[UID-ROUTE]`.
   - **Choose the role by what the user does with it.** A test action is only valid on a role that can take it: `check` and `uncheck` act on a checkbox or switch, `fill` on a textbox or combobox, `select` on a combobox, and a `count` is of a `repeats` element `[TP-UI-TARGET]`. A control that is clicked to flip is a checkbox or switch, not a button; a title that is not operable is a heading, not a button. The generated surface check opens every screen and asserts that each non-repeating element is on it by role and name, before any scenario runs, so a design the built surface cannot match fails once and names the element.
   - **Interaction policy is the platform's, not the design's.** Two things hold for every surface and the record has no field that changes them. First, a control's own state shows the user's gesture at once: a clicked checkbox is checked, a committed edit shows the new text, a deleted row is gone, and a call in flight neither disables the control nor blocks unrelated input; the design chooses only how to reconcile with the server's answer (roll back with a notice, or a pending style). The generated tests assert this under an injected server latency (the latency harness), so a surface that waits for the server before showing the user's own gesture fails its generated test. Second, every control has a native role and an accessible name that says what it does. Do not state a behaviour constraint in `content` that the customer never stated: the UI-design review rejects an untraced one.
3. **Verify** (only your own output; fast checks): every screen, flow, and state in the concept traces to a use case or persona captured in the surface's UX requirements — no invented scope; no production UI code exists yet; the committed system design and any frozen service contracts are unchanged.
4. **Stop.** Do not mark phase status (the Manager owns that) and do not merge. Leave the PR open for the gate.
