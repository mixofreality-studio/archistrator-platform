# /service-detailed-design

> The Detailed Design step of a service activity: design and freeze the component's public contract, then hand it to the architect for review before construction begins.

**Arguments** — `$ARGUMENTS` is `<component_id> <activity_id>` (two space-separated tokens; `component_id` may be empty for non-component activities). Parse once; do not swap them. Work lands on the shared activity branch `activity/<activity_id>` and its single PR — you are contributing commits to a PR that already exists (or open it if this is the first phase). Do NOT open a second PR.

**Agent + skills.** Work to the standard of whichever agent the Manager assigned this activity's worker class to — **`senior-developer`** (`.claude/agents/senior-developer.md`), the default under the senior hand-off model, or **`system-architect`** (`.claude/agents/system-architect.md`) when the Manager has assigned this contract to the architect directly. The assignment is Manager-owned; read it per [[the-method-project-state]] before starting — do not guess. Follow **[[the-method-service-contract]]** and **[[the-method-project-state]]** for all reading/updating of `.aiarch/state/project.json`.

**Goal / intention.** Per Appendix B, the service contract is where a clean architecture either holds its area of minimum cost or loses it: get a contract's granularity or shape wrong and the project's per-service and integration cost curves both turn nonlinearly worse, regardless of how sound Phase 1's decomposition was. Appendix B calls contract design "a time-consuming, highly contemplative task" — simple in its rules but never simplistic — and warns that even senior developers usually need architect mentorship before they can do it correctly. Per ch. 14's senior hand-off, the architect hands off only a gross outline of each service soon after the SDP review; the senior developer then plays "junior architect" and performs the actual detailed design — the public interface(s), message and data contracts, and internal structure — for this one component, building on the Requirements-phase scope note. Every detailed design goes back to the architect for review and amendment before any junior developer is allowed to construct against it; skipping that review is what produces contracts resembling a single overloaded interface instead of a reusable, cohesive facet. "Done" means a frozen, reviewed contract that a junior developer can build against without further clarification. This step must NOT skip architect review, must NOT hand an unreviewed design to construction, and must NOT let the contract balloon past the size and shape limits in [[the-method-service-contract]].

**Checks.** Call `run_checks()` until it reports every check passing, and finish with one full `run_checks()` call. Do not run the checks yourself.

## Steps

> **Operator notes first.** First call `getOperatorNotes`; if it returns notes, act on them before anything else. They are the operator's steer for this attempt (a send-back, retry or re-queue note) and outrank the defaults below.

> **A design gap is a failure, not a state.** If the committed design leaves something unimplementable, such as a relationship no dynamic view calls, say so and stop with your work unpublished rather than recording "Pending architect amendment" or anything like it: nothing ever reads such a note, and the activity would finish with the gap in it.

> **State changes go through the `aiarch-state` MCP tools, not hand-edits.** Where a step below says to record a service contract, phase artifact, or testing artifact and "commit onto branch", do it with the matching tool — `recordServiceContract` / `recordPhaseArtifact` / `recordTestingState` — and finish with `publishDraft`. Do **not** hand-edit `.aiarch/state/project.json` or run `git` for state; only source/doc **files** (code, docs) are git-committed by you. See [[the-method-project-state]].

1. **Read what you need** from `.aiarch/state/project.json` per [[the-method-project-state]]: the activity, the component's Requirements-phase scope note, its entry (layer, relationships) in the committed system design, its encapsulated volatility, and its sync/queued + pub/sub treatment in the committed operational concepts.
2. **Produce** the phase artifact: the frozen service contract — operations, data contracts, error model, idempotency — recorded to `.aiarch/state/project.json` → `.serviceContracts["<contractKey>"]` (the component's `contractKey` — camelCase, server-derived from its kebab id, e.g. `billingEngine` for `billing-engine`; `recordServiceContract` files it there for you, see [[the-method-project-state]]) via `recordServiceContract`, then committed onto branch `activity/<activity_id>` and handed to system-architect for review via [[the-method-review-routing]].
   - **`goPackage`** is `internal/<layer>/<leaf>`: `internal/resourceaccess/todolist`, `internal/manager/list`. The layer directory is lowercase and the leaf is one lowercase word; every app lays its components out this way.
   - **`interface.layer`** is one of `engine`, `manager`, `resourceaccess`, `utility`. A Client authors no contract: `recordServiceContract` refuses one.
   - **Every name you record becomes Go, so it obeys Go.** `interface.name` and every operation name are exported identifiers: a capital first letter, then letters and digits (`Publish`, not `publish` or `Pub-lish`). Record the capitalised spelling; a dynamic view's label such as `publish(ListChanged(...))` still reaches `Publish`, because labels are matched ignoring case. A param name is a Go identifier, not a keyword, and not one the generated code around it uses (`rc`, `ctx`, `err`, `result`, `ok` and a few more: `recordServiceContract` names them all). `$defs` names and property names must be able to become Go type and field names, so write `dueDate`, not `due-date`, and declare every type an operation references. `recordServiceContract` refuses anything else, because a bad name stops generation for the whole project or leaves a package no fake or caller can reach.
   - **`interface.name`** of an Engine ends in `Engine`, and of a ResourceAccess in `Access`.
   - **Every Engine, ResourceAccess and Manager operation declares `error: true`**, even a total one, whose implementation simply returns nil. The arch gate refuses anything else at construction, where the contract is frozen, so `recordServiceContract` refuses it here. A Utility or Client operation may declare `error: false`.
   - **`infra`** (ResourceAccess, and any Utility fronting a resource) names the infrastructure the component is built on, chosen from the approved menu: `Anthropic`, `ExternalHTTP`, `Git`, `GitHub`, `GitHubActions`, `Ollama`, `Postgres`, `Profiled`, `Replay`, `Temporal`. It is required on a ResourceAccess. A Resource's name is not an infra name: a service reached over HTTP (an identity provider, a payment API) is `ExternalHTTP`. `recordServiceContract` refuses anything else and names the menu.
3. **Verify** (only your own output; fast checks): walk the App C §6 standard check embedded in [[the-method-service-contract]] (operation count in range, no property-like operations, ≤2 contracts per service, layer interaction rules respected). Every operation you add must be called by a use case's dynamic view (methodcheck `TP-OP-REACHED` rejects it otherwise): add the call (or a use case) or don't add the op. Do not mark the contract `FROZEN` until that check passes and architect review is scheduled.
4. **Stop.** Do not mark phase status (the Manager owns that) and do not merge. Leave the PR open for the gate.
